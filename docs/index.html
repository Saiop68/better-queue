BetterQueue

A Redis-backed rate limiter and job queue for Node.js

Run one limiter per tenant, per user, or per route — across every process in your fleet. Queue state lives in Redis, so memory stays flat and a crashed process doesn't lose its jobs.

Install

# npmjs.org — no token, no account, works immediately
npm install @destroyer777777/betterqueue ioredis

Use it

import { WorkerPool, DistributedLimiter } from '@destroyer777777/betterqueue';

// One pool for the whole process.
const pool = await WorkerPool.create({
  redis: { host: 'localhost', port: 6379 },
  workers: 16,
});

// A limiter per tenant. State lives in Redis, not in this process.
const limiter = new DistributedLimiter({
  id: 'tenant:acme',
  maxConcurrent: 5,
  minTime: 100,
});

await limiter.schedule(async () => {
  await doWork();
});

await pool.stop();

BetterQueue vs Bottleneck

Measured on the same machine, same Redis, each library in its own process. 1000 limiters, 51,000 jobs. Reproduce it yourself — the script is in the repo.

Honest caveat: Bottleneck has zero dependencies and is very good at what it does. If you need one process and a handful of limiters, Bottleneck is the lighter choice. BetterQueue earns its dependencies when you're running many limiters, more than one process, or jobs that must survive a restart.

What you get

Flat memory

Limiters are thin handles. Queue state lives in Redis, so 1,000 limiters cost about the same as 10.

One ticker

A single global timer for the whole process. No timer per limiter, no timer per queue.

Real priority

Jobs are ordered by priority across every process, computed server-side in Redis.

Crash recovery

Kill a worker mid-job and the job is re-queued by another process, not lost.

Delayed jobs

scheduleAt() for anything that needs to happen later. Bottleneck can't do this.

Atomic state

Every state transition is a Lua script, so two workers can't race the same queue.

Bottleneck compatibility

Already using Bottleneck? The LimiterManager entry point keeps the same registerFeatureConfig / getLimiter / schedule() shape, so most migrations are an import-path change. 

import { limiterManager } from '@destroyer777777/betterqueue/LimiterManager';

limiterManager.registerFeatureConfig('member-add', {
  maxConcurrent: 5,
  minTime: 250,
});

const limiter = limiterManager.getLimiter(tenantId, 'member-add');
await limiter.schedule({ id: jobId }, async () => { /* work */ });

Not supported (yet)

Being straight about this: Redis Cluster, node-redis v4, sliding-window rate limiting, cron/scheduled groups, and reset()/cancel() are not implemented. Crash recovery re-queues work but does not resume it mid-flight.

Get involved

The project is young and the roadmap is on the contributing page. Redis Cluster support, a node-redis adapter, a sliding window, and job inspection are all open and all welcome.
